# ADR-0005: Publish immutable document versions through an active-version switch

- Status: Accepted
- Date: 2026-08-30

## Context

Parsing, chunking, embedding, and indexing are multi-stage operations that can fail independently. Updating an active document in place can expose mixed old and new chunks, partial indexes, mismatched citations, or content generated by different model profiles.

## Decision

A logical document owns immutable versions. Each ingestion creates a candidate version with version-scoped S3 artifacts and Redis keys.

A candidate becomes visible only after:

1. original and normalized artifacts exist in S3;
2. the chunk manifest is durable and its digest recorded;
3. the expected chunks exist in the target search projection;
4. verification succeeds;
5. one PostgreSQL transaction marks the version `READY`, switches `documents.active_version_id`, supersedes the old version, increments the knowledge-base revision, and records outbox/audit events.

Search hits are validated against the current active version before being returned. Old Redis projections are removed asynchronously.

## Consequences

Positive:

- no partially indexed version becomes visible;
- citations remain tied to immutable source content;
- parser, chunker, embedding, and index-profile migrations are reproducible;
- rollback can switch to a prior valid version under an explicit operation;
- stale Redis cleanup cannot expose obsolete content.

Costs:

- temporary duplicate storage during processing and retention;
- publication requires cross-system verification plus a database transaction;
- background retirement and lifecycle policies are required;
- active-version checks add a small retrieval cost that should be cached safely.

## Invariant

Every externally returned chunk belongs to the current active version of its logical document and includes enough metadata to fetch that exact immutable source later.
